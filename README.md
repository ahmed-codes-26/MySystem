# MySystem

A personal workspace for habit tracking, financial organization and securely stored account credentials. Built with React, Express and MongoDB, with a responsive interface and three configurable themes.

## Features

- **Habits:** weighted daily tracking, sleep logging, progress charts and a 365-day activity heatmap.
- **Finance:** income and expenses, balances, savings goals, monthly budgets, recurring payments and owed amounts. Values use whole Pakistani rupees. No bank connections or real money transfers.
- **Passwords:** searchable accounts, pinned favorites, custom fields, password generation and encrypted storage.
- **Appearance:** consistent typography, mobile layouts and Tangerine, Raspberry and Pure Ink themes.

This is a single-owner application. Multi-user accounts, MFA and password recovery are not implemented.

## Technology

React 19, React Router, Vite, Tailwind CSS, Express 5, Mongoose, MongoDB, Zod, bcrypt and JSON Web Tokens. npm workspaces manage the client and server from the repository root.

## Requirements

- Node.js 22.12 or newer; Node.js 24 is supported.
- npm and a MongoDB deployment supporting transactions, such as MongoDB Atlas or a replica set.

## Local setup

1. Install dependencies from the repository root:

   ```sh
   npm ci
   ```

2. Copy `.env.example` to `server/.env` and populate the required values below. The server reads **server/.env**, not a root environment file. Hosting environment variables are also supported.
3. Generate the owner password hash:

   ```sh
   npm run hash-password
   ```

   Enter the password at the hidden prompt. Put the resulting hash in `ADMIN_PASSWORD_HASH`. Do not pass passwords as command arguments.

4. Generate independent random values for the JWT secret and vault key. Run this command separately for each value:

   ```sh
   node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
   ```

5. Start both services:

   ```sh
   npm run dev
   ```

Open http://127.0.0.1:5173 and sign in with the owner password. The API listens on http://127.0.0.1:5000. If Vite selects a different port, use the URL printed in the terminal and update `CLIENT_ORIGIN` as needed.

## Configuration

| Variable | Purpose |
| --- | --- |
| `MONGODB_URI` | MongoDB connection string. The application uses the `mysystem` database. |
| `JWT_SECRET` | Independent random signing secret, at least 32 characters. |
| `ADMIN_PASSWORD_HASH` | bcrypt owner-password hash generated by the supplied command. |
| `VAULT_ENCRYPTION_KEY` | Independent 32-byte key represented by 64 lowercase hexadecimal characters. |
| `CLIENT_ORIGIN` | Exact frontend origin, e.g. `http://127.0.0.1:5173` locally or your HTTPS production origin. |
| `PORT` | API port; default `5000`. |
| `NODE_ENV` | `development` locally; `production` when deployed. |
| `APP_TIMEZONE` | Application timezone; default `Asia/Karachi`. |

Never commit populated environment files, keys, database exports or credentials. Back up the vault key separately from the database: losing it makes stored credentials unreadable. Changing it without a migration also makes existing records unreadable.

The database starts empty. `npm run seed` optionally inserts clearly labelled fake demonstration data; do not run it if you want a clean personal workspace.

## Commands

| Command | Description |
| --- | --- |
| `npm run dev` | Start the local client and API with reload support. |
| `npm run build` | Build the frontend into `client/dist`. |
| `npm start` | Start Express, serving the API and built frontend. |
| `npm test` | Run database-independent client and server tests. |
| `npm run test:finance:integration` | Exercise Finance against an isolated temporary database. |
| `npm run test:security` | Exercise authentication, request protection and vault behavior against an isolated temporary database. |
| `npm run hash-password` | Generate an owner-password hash using hidden input. |
| `npm run vault:migrate` | Check for legacy vault ciphertext; add `-- --apply` to migrate. |

Integration suites need valid server configuration, database connectivity and permission to create and remove their uniquely named temporary test databases. They do not clear the application database. The legacy `test:integration` script instead uses the configured application database and requires `TEST_PASSWORD`; prefer the isolated suites above for routine verification.

## Deployment

Deploy as one Node web service. Express serves both the compiled React application and `/api`, so a separate frontend service is unnecessary.

1. Push source files and `package-lock.json` to a private or public GitHub repository. Local environments, dependencies, reference screenshots and generated builds are ignored.
2. Configure the host to use a supported Node version, with the repository root as its working directory.
3. Set the build command to `npm ci && npm run build` and the start command to `npm start`.
4. Add the required environment variables through the hosting provider. Set `NODE_ENV=production` and `CLIENT_ORIGIN` to the exact public HTTPS origin. Use independent high-entropy secrets and a database connection with TLS and certificate verification enabled.
5. Restrict Atlas network access to the hosting service's outbound addresses or private networking. Give the runtime database user only the permissions needed for `mysystem`. Do not give the public runtime broad administrative privileges for test-database creation.
6. Terminate HTTPS at one trusted reverse proxy and prevent direct public access to the origin server. The production app trusts one proxy hop. Use `/api/health` for health checks.
7. Verify sign-in, Secure cookies, logout and the public response headers before storing sensitive information. Enable provider MFA and encrypted backups, and test recovery.

Do not expose the Vite development server publicly. A static-only hosting service cannot run this application's API.

## Security model

Private endpoints require a signed JWT cookie backed by a revocable server-side session. Sessions have a seven-day idle expiry and a 30-day absolute limit. Production cookies use Secure, HttpOnly, SameSite and the `__Host-` prefix. Login attempts have persistent throttling. Mutating requests require JSON, a custom header and trusted browser origins; request schemas reject unexpected input.

Vault records use AES-256-GCM with authenticated record IDs. Account lists return metadata; full fields are fetched for the selected account. The server holds the decryption key: this is server-side encryption, **not end-to-end or zero-knowledge encryption**. Financial records rely on database storage encryption and transport TLS rather than application-level encryption.

No system is guaranteed immune to compromise. Single-factor login, host security, browser/device security, database permissions and backup handling remain material considerations. The audit documents tested controls and deployment limitations, not a certification of a public deployment.
